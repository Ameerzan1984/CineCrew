# Generation scheduling foundation

This is a PostgreSQL-backed scheduling library and an internal HTTP adapter, not an active provider worker. It is not yet called by the web gateway or wired to film production, Higgsfield, or object storage. No credentials or vault keys are stored or returned here.

Apply `migrations/001_scheduler.sql` to PostgreSQL and instantiate `Scheduler(connect, authorize)`, where `connect` returns a new `psycopg` connection configured with `psycopg.rows.dict_row`. The host service must authenticate `actor` itself. `register_resource` registers an owner-owned provider capability; `grant` records explicit per-project consent and budget. `enqueue` uses a project-scoped idempotency key. `claim` reserves the estimate and assigns the lowest proportional committed usage among eligible contributors. Row locks and a project advisory lock coordinate workers; resource locks protect concurrency across projects. `renew_lease` extends only the current, unexpired claim when its token matches; it locks the row before checking wall-clock expiry so a lock wait cannot revive an expired claim. `finish` and `fail` use the same lock-then-check rule and reject expired or stale leases. `finish` writes the actual cost and result reference. `fail` retries only when the provider definitely did not accept or charge the request; all other failures remain `uncertain` with their reservation intact. `expire_leases` marks timed-out work uncertain and `reconcile` requires a trusted operator to check provider records before retry or completion. `progress` returns persisted status counts. Revocation blocks new claims; it cannot cancel submissions already accepted by a provider.

Budgets and cost values are integer millionths of the declared ISO currency. Estimates enforce reservation limits but do not guarantee a provider will never charge more: a provider must support a hard spending cap to guarantee that. Actual charges, including overruns, are recorded, after which no further work fits an exhausted budget. A provider adapter must verify estimated prices and capability semantics, apply provider rate limits, use the stable `provider_request_key` only if supported, and never promise provider-side idempotency without proof. Retries are unsafe when the provider may have accepted a request; reconcile those manually. The result reference must identify an access-controlled private object, not a bearer URL.

Run policy tests with `python -m pytest services/generation-worker/tests`. Set `CINEMESH_TEST_POSTGRES_URL` to a disposable PostgreSQL database to run the integration test; it creates and drops a randomly named test schema. Production still needs migration management, provider metering, administrative reconciliation access control, a worker loop that periodically invokes lease renewal, cancellation, alerts, observability, and testing against real infrastructure. The scheduler is not yet connected to the web gateway or a live provider.

## Internal API boundary

`api.py` is an optional internal FastAPI adapter: install the requirements, apply the CineMesh database migration and this service migration to the same database, set `DATABASE_URL` and a long random `GENERATION_SERVICE_TOKEN`, then run `uvicorn api:app --host 127.0.0.1 --port 8002` from this directory. Keep the token in server-side secret storage and do not expose this service to browsers or public networks. The token must be distinct from all other service tokens.

A trusted gateway authenticates a user session, removes any client-supplied internal headers, and forwards the verified user UUID in `X-Cinemesh-Actor` along with the secret `X-Cinemesh-Service-Token`. The adapter independently checks the authoritative `users`, `films`, and `film_contributors` tables. Owners and editors may submit jobs and grant their own resources; viewers may read progress; only the resource owner may revoke their grant. The gateway must hold the token exclusively: anyone with it can impersonate arbitrary actors, so direct client access or token disclosure breaks the security boundary. Project authorization is checked before the subsequent scheduler transaction; concurrent removal of membership is not guaranteed to invalidate a request already in progress. Strong immediate revocation requires coordinated locking or database row-level security integrated with membership updates.

Endpoints: POST `/resources`; POST `/projects/{id}/grants`; DELETE `/grants/{id}`; POST `/projects/{id}/jobs`; GET `/projects/{id}/progress`. There are deliberately no HTTP claim, completion, credential or provider-execution endpoints. A future authenticated worker integration must implement those safely. The current gateway does not call these endpoints, and no provider jobs run.
