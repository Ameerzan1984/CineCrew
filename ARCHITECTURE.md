# CineMesh architecture

CineMesh preserves the Apache-2.0 CineCrew source, attribution, configs and examples. The CineCrew pipeline represents a film as FilmDSL (`SceneBlueprint`) with stable asset IDs. Its full configured agent sequence turns a narrative into story, staging, resolved visual prompts and production jobs. Running this full LLM pipeline requires an LLM backend configured in the environment; offline `ProductionOperatorAgent.build_from_blueprint()` only turns an already prepared FilmDSL into job specifications.

`apps/web` is the Next.js social and production interface. It authenticates users, enforces project access and talks to PostgreSQL through `packages/database`. Its Higgsfield API credentials are per-user encrypted data. The web routes support a documented Seedance 2.5 generation flow for a contributor's own scene, but this does not by itself make the full agent and worker pipeline automatic.

The Next.js server talks to `services/film-engine` (FastAPI) with a service secret. The engine supports SQLite for local development and a dedicated `cinemesh_engine` PostgreSQL schema for shared run inputs, FilmDSL, stage outputs and checkpoints. The development Compose stack is configured to use PostgreSQL. Run claims and film advancement use PostgreSQL advisory locks in addition to unique constraints. The hosted CI test passed on commit `b160c603be93f54f7e353849ab6e0f4547f51b39` (push run [41201209615](https://github.com/Ameerzan1984/CineCrew/actions/runs/41201209615), PR run [41201213840](https://github.com/Ameerzan1984/CineCrew/actions/runs/41201213840)): it imports a legacy SQLite run/checkpoint into an isolated PostgreSQL schema, restores the checkpoint after a second FastAPI lifespan, and serializes concurrent idempotent advances. Production backup/restore, actual process-kill recovery, multi-replica deployment, and lease fencing against a long-paused stale worker remain unverified. PostgreSQL also stores a per-film CineCrew run registry (run ID, creator, model, status and stage) for browser discovery; the engine schema stores the resumable content. Keep the engine private. `services/generation-worker` has PostgreSQL scheduling primitives, but they are not yet connected to live provider dispatch. `services/render-worker` concatenates compatible local clips using FFmpeg.

The engine writes a completed stage's checkpoint and status in one database transaction. On resume after a stale heartbeat, it reconciles unfinished stage markers against saved checkpoints: a checkpointed stage is restored as complete, while a stage without a checkpoint is marked interrupted and retried. SQLite tests cover the simulated crash window; hosted PostgreSQL CI run [41201209615](https://github.com/Ameerzan1984/CineCrew/actions/runs/41201209615) covers checkpoint recovery after a new FastAPI lifespan and concurrent idempotent film advancement. Neither test proves a real process kill, database backup/restore, or multi-replica safety.

PostgreSQL stores collaboration notifications and migration 013 adds one-to-one private conversations, messages, read state and directed blocks. Migration 014 adds user/film reports, a deployment-configured admin email allowlist, audited moderation actions, and a film visibility restriction that is enforced by public feed, profile, watch, comment, like, media and republish routes. The moderation UI supports dismissal and film hide/restore; it does not suspend accounts or moderate comments. Local unit/type/build checks passed. The first moderation rerun exposed a real mobile topbar hit-target overlap: the profile button intercepted Sign out. Commit `84d896dfee608deab3b0dbe37dd1bb1046022bd9` narrows the mobile profile action and tests the admin in a separate session; hosted push and PR runs [41203366722](https://github.com/Ameerzan1984/CineCrew/actions/runs/41203366722) and [41203371674](https://github.com/Ameerzan1984/CineCrew/actions/runs/41203371674) passed. Group chat, general activity notifications and broader account/content moderation remain open.

Migration 015 adds one 1–5 star written review per user and published film. The Watch page exposes the public rating average and recent reviews while allowing signed-in users to create, edit or delete only their own review; drafts and moderator-hidden films reject review reads and writes. PostgreSQL integration and desktop/mobile Playwright coverage have been added; the local database services are unavailable, so those suites await hosted CI.

## What has been proved live

On 2026-10-31 a temporary local diagnostic:

- Submitted two real 4-second Seedance 2.5 API generations under one user's API credential.
- Used the first clip as the video reference for the second.
- Downloaded both outputs locally and assembled them with the render worker into an 8.192-second MP4.
- Used CineCrew's real `ProductionOperatorAgent` to build two job specs from manually prepared FilmDSL.

The test did not run the website, PostgreSQL or FastAPI gateway, did not generate the script or FilmDSL with an LLM, and did not use two contributors. The test clips are local ignored artifacts, not a published or persisted CineMesh film. MCP OAuth discovery also worked in a temporary test, but the selected account could not generate through MCP because it requires Plus or higher.

This remains an experimental platform, not a production-ready social network. See [project memory](docs/PROJECT_MEMORY.md), [Higgsfield integration facts](HIGGSFIELD_INTEGRATION.md), [development plan](DEVELOPMENT_PLAN.md), and [next steps](docs/NEXT_STEPS.md). Never expose the internal film service publicly; keep API keys and OAuth credentials out of code, logs, browser storage and Git.
