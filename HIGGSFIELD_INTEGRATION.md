# Higgsfield integration notes

Reviewed 2026-10-29 against the provider's current documentation. The REST client in `packages/providers/src/higgsfield-api.ts` and the authenticated connections endpoint are server-side building blocks; they are not yet wired into the generation queue or media storage. No real credential, connection, charge, or generation has been tested.

The authenticated `/api/connections` endpoint stores each user's API key ID and secret as AES-256-GCM ciphertext tied to that user's ID. Set `HIGGSFIELD_VAULT_KEY` to a random 32-byte base64-encoded value in the server's secret manager or environment, and apply the database migrations. Keep this key stable and backed up securely; replacing it without re-encrypting the credentials makes them unreadable. Never commit it. Saving credentials reports only that they are configured. Verification requires an existing request ID from that API account and reports the timestamp of the last successful authenticated status check. That timestamp is historical and does not establish current availability or prove that a key has not since been revoked. A newly created API account without a previous request cannot use this no-charge verification path yet. Models, jobs, usage and balance are not retrieved by the endpoint.

## API

The [API documentation](https://docs.higgsfield.ai/docs/authentication) specifies a key ID and secret and the `Authorization: Key ID:SECRET` header. The [request lifecycle](https://docs.higgsfield.ai/docs/concepts/requests) specifies asynchronous submission, an `Idempotency-Key`, request ID, status and cancel URLs, and the `queued`, `in_progress`, `completed`, `failed`, `nsfw`, and `canceled` states. Cancel succeeds only while queued and returns 202. The adapter accepts a model path and parameters selected using the current model's own documentation. It validates request URLs, refuses redirects, exposes sanitized HTTP errors, and returns media URLs without downloading them. A successful authenticated submission or status lookup verifies the credentials for that request; merely storing a key does not. Status and cancellation take a persisted request handle so they can resume in a new process.

There is no verified discovery, estimate, balance, or usage endpoint in the shared documentation reviewed here, so this adapter does not invent those operations. [Model discovery](https://docs.higgsfield.ai/docs/llms.txt) starts at the provider's console and the supplementary OpenAPI document is not a complete catalog. A successful request does not prove access to every model. The caller must enforce per-user ownership, consent, concurrency, spending limits, and authorization; use encrypted server-side credential storage; persist handles and idempotency keys before retry; validate model inputs; and copy completed media to controlled storage using an SSRF-safe downloader. Poll with backoff and jitter according to the [polling guide](https://docs.higgsfield.ai/docs/concepts/polling). Results expire; do not treat provider URLs as durable storage.

Higgsfield's API and MCP use separate accounts and billing: API spending comes from a USD balance, while MCP generation consumes Higgsfield plan credits. Neither can stand in for the other. See the [API help page](https://higgsfield.ai/creator-hub/help-center/integrations/what-is-the-higgsfield-api) and [MCP help page](https://higgsfield.ai/creator-hub/help-center/integrations/what-is-higgsfield-mcp).

## MCP

Higgsfield publishes `https://mcp.higgsfield.ai/mcp` and says third-party MCP clients can use OAuth. Its [protected resource metadata](https://mcp.higgsfield.ai/.well-known/oauth-protected-resource/mcp) describes authorization-code PKCE and named client capabilities, but this review did not establish a supported client registration method or redirect URI for a standalone CineMesh deployment. The authorization server metadata was not accessible during this review. Therefore, OAuth for this independent app is not implemented or claimed as connected; adding it requires verified registration and redirect support, per-user encrypted token storage, state and PKCE validation, refresh/revocation handling, and real end-to-end testing. API remains an independent option.

## Local tests

`npm test --prefix packages/providers` covers documented request headers and lifecycle with a mocked HTTP transport, resumption, invalid and attacker-controlled URLs, sanitized authentication errors, and malformed responses. `node --test apps/web/test/provider-vault.test.ts` checks encryption, user binding and tamper detection. Mock HTTP responses are not evidence of provider access. A real short generation requires authorized API credentials, funded API balance, a model and parameters confirmed in its current documentation, explicit spend authorization, and safe media storage.
